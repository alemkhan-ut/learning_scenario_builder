# # CSharp & Unity Style Guide

## Рекомендации по форматированию

### Код

1. Принцип SOLID и KISS должен быть соблюден в коде без исключений
2. Имена констант: **UNDER_SCORE**
3. Имена классов, методов, перечислений, публичных полей, свойств и пространств имен: **PascalCase**
4. Имена локальных переменных, параметров: **camelCase**
5. Имена полей и свойства с модификаторами доступа `private, protected, internal & protected internal` : **_camelCase**
6. Имена содержащие аббревиатуру или сокращения: `MyRpc`вместо `~~MyRPC~~`
7. Имена интерфейсов начинаются с `I`: `IInterface`
8. Всегда должны присутствовать открывающие и закрывающие фигурные скобки в любом теле скрипта без исключений
9. События должны иметь в конце наименования слово `Event` (`OnLoadedEvent`)
10. Все методы который обрабатывают события должны именоваться как событие которое обрабатывает, с постфиксом `Handler` (`GameOverEventHandler`, `EnemyKilledEventHandler`, `HeroSpawnEventHandler`) исходя из этого у одного события не должно быть несколько подписчиков, одно событие - один подписчик в одном классе
11. Корутины должны иметь в конце наименования слово `Coroutine` (`DownloadCoroutine`)
12. Название методов/свойств которые возвращают какие-либо данные должны описать это в наименовании ( `GetResource()`, `CheckNetwork()` )
13. Если в скрипте ссылаются к `GetComponent()` у текущего обьекта, то у объекта к которому ссылаются должен присутствовать атрибут у класса (`RequireComponent(typeof(ClassName))`)
14. Все необходимые внутренние запросы у объекта на `GetComponent()`, должны быть захешированы/проинициализированы только в `Awake()`;
15. Обязательно использовать `namespace` в каждом файле в формате: `ProjectName.NamespaceName` - `Fungarium.Services.Core` , `Fungarium.Localization` , `Fungarium.Settings`
16. Принцип DRY должен быть соблюден в коде без исключений
17. Принцип YAGNI должен быть соблюден в коде без исключений
18. Использовать `nameof()` вместо строковых литералов для имен методов, свойств, классов и т.д.
19. Использовать `string.IsNullOrEmpty()` и `string.IsNullOrWhiteSpace()` вместо сравнения с `null` или пустой строкой
20. Преимущественно использовать приватные методы и поля, если нет необходимости в публичном доступе, для доступа в инспекторе использовать `[SerializeField]` для полей

### Файлы

1. Имена файлов и имена каталогов: **PascalCase** [ MyClass.cs ]
2. Имена файлов должны совпадать с именем основного класса в файле
3. Предпочитайте иметь один класс в одном файле
4. Предпочитайте разделять `enum`, `struct` по собственным файлам

### Организация

1. Модификаторы расположены в следующем порядке `public protected internal private new abstract virtual override sealed static readonly extern unsafe volatile async`
2. `using` объявления пространств имен идут вверху, перед пространствами имен, порядок в алфавитном порядке, кроме `System` которые всегда идут первыми
3. Структура класса сверху-вниз
    1. События, Делегаты [`Events&Delegates`] (public , private) 
    2. Константы [`Constants`] (public, private)
    3. Статические поля [`Static`] (public, private)
    4. Поля только для чтения [`Readonlies`] (public, private)
    5. Перечисления [`Enums`] (public, private)
    6. SerializeField поля [`SerializeFields`] (public , private)
    7. Поля [`Fields`] (public, private)
    8. Свойства [`Properties`] (public, private)
    9. Конструкторы [`Constructs`]
    10. MonoBehaviour/Unity методы [`MonoBehaviours`]
    11. Простые методы [`Methods`] (public, private)
    12. Callbacks [`Callbacks`]
4. Имя класса должно быть существительным, должен передавать суть класса
5. Обязанности класса не должны выходить за его рамки ответственности
6. Не допускать в каталогах проекта, и в иерархиях сцен, наличие не сформулированных названий не передающие смысла и назначения объекта и его дочерних объектов, у файлов и объектов по типу `Image, Image(1), GameObject, Sprite, Фото_3, Test`. Правильная реализация: `Attack Handler` (родительский объект) содержит `Attack Handler Sprite Renderer` (содержит компонент `Sprite Renderer` для `Attack Handler`), `Attack Handler Button` (содержит кнопку для `Attack Handler`)
7. Повторяющиеся элементы UI и игровые объекты выносятся в отдельный `Prefab` и используются в сцене как его экземпляры, а не как копии объектов в сцене (подробно в разделе «Рекомендации по Prefab в Unity»)
8. При использовании Unity Localization, все локализуемые строки должны быть вынесены в `String Table` и использоваться через `LocalizedString` типы используя атрибуты в инспекторе а не через `string` литералы, для локализуемых изображений использовать `LocalizedAsset` типы
### Правила пробелов

1. Разрыв строки перед открытием фигурных скобов
2. Разрыв строки между закрывающей фигурной скобкой и `else`
3. Фигурные скобки используется даже тогда когда они необязательны
4. Пробел `if / for / while` и т.д. и после запятых

## Рекомендации по коддингу на C#

### Константы

1. Переменные и поля, которые могут быть созданы как `const`, всегда должны быть созданы как `const`
2. Если создание `const` невозможна то `readonly` может быть подходящей альтернативой
3. Предпочитайте именованные константы магическим числам

### Поля

1. Все поля должны обязательно иметь модификаторы доступа без исключений

### Свойства

1. Для однострочных свойств, доступных только для чтения используйте тело выражения (`=>`)
2. Для всего остального используйте более старый `{ get; set; }` синтаксис
3. Все методы должны обязательно иметь модификаторы доступа без исключений

### Массив против Списка

1. Предпочитайте `List<>` когда размер контейнера может меняться
2. Предпочитайте массивы когда размер фиксирован и известен во время построения
3. Предпочитайте массивы для многомерных массивов

### Именование пространств имен

1. Не заставляйте макет файлов / папок соответствовать пространствам имен

### Вызов делегатов

1. При вызове делегата используйте `Invoke()` и используйте условных оператор `null` -  `SomeDelegate?.Invoke()`

### Ключевое слово `var`

1. Всегда используйте явный тип вместо использования `var`

### Атрибуты

1. Атрибуты должны отображаться в строке над полем, свойством или методом, с которыми они связаны, отделенные от элемента новой строкой.
2. Несколько атрибутов должны быть разделены символами новой строки. Это упрощает добавление и удаление атрибутов и упрощает поиск по каждому атрибуту.

## Рекомендации по UI в Unity

1. UI должен быть адекватно масштабирован под разные разрешения экранов

## Рекомендации по Prefab в Unity

Prefab — способ по умолчанию для любого объекта сцены. Объект собирается прямо в сцене только в случаях, перечисленных в пункте «Исключения».

1. Prefab-ом оформляется любой объект или группа объектов, если выполняется хотя бы одно условие: встречается в сцене или в разных сценах больше одного раза, создаётся в рантайме, содержит компонент проекта (`MonoBehaviour` из `StickmanCarpetEmpire`), является окном, панелью, кнопкой или другим элементом UI
2. Объекты в рантайме создаются только через `Instantiate()` из Prefab, ссылка на который задаётся через `[SerializeField]` или конфиг. Сборка объекта в коде через `new GameObject()` + `AddComponent()` запрещена
3. Вариации одного объекта (другая модель, цвет, параметры) делаются через `Prefab Variant` от базового Prefab, а не копированием Prefab
4. Составные объекты собираются из вложенных Prefab (`Nested Prefabs`): общая часть (например кнопка, счётчик, слот) — отдельный Prefab, который переиспользуется внутри других
5. Настройки, общие для всех экземпляров, задаются в самом Prefab. Override в экземпляре на сцене допустим только для данных конкретного места: позиция, поворот, ссылки на объекты сцены. Остальные override применяются (`Apply`) в Prefab или выносятся в `Prefab Variant`
6. Prefab самодостаточен: не ищет объекты сцены через `Find()`, `FindObjectOfType()` и аналоги. Зависимости от сцены передаются при инициализации экземпляра или через сериализованные ссылки, назначенные в экземпляре
7. Корневой объект Prefab называется так же, как файл Prefab. Правила именования из пункта 6 раздела «Организация» распространяются на всю иерархию Prefab
8. Исключения, когда объект допускается оставить в сцене без Prefab: уникальные объекты окружения сцены без компонентов проекта (`Directional Light`, `Global Volume`, `EventSystem`), объекты, созданные вендорным кодом (например `GamePushSDK`)
